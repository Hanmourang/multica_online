画面 2 · 为什么现在「左侧模块」与「右侧说明」接不上：说明的主语是需求，不是模块

现状三条链各自断开：①主键借道——左栏只认 graph_node_id，未桥接模块 canSelect=false 根本点不进去；②说明借道——右栏「交付预期」读的是 issue.goal，「模块与细节绑定」读的是「需求↔模块」关联，切模块时说明不会换，换需求下拉时说明才换；③详解易碎——inspectorPoints 每次从当前 HTML 现抽，未标注 data-fp 就整列「待标」，标了也不沉淀成可绑定实体。TO-BE 把主语换回模块：module.id 一条主键贯穿左栏、版本、说明、功能点、绑定。

画面 3 · 模块说明是一个有版本的实体：结构化段落 + 功能点引用 + 可审阅 diff

画面 4 · 让 Agent 自己迭代原型与说明：提案两段式，发布必须成对

Agent 可以自主产生原型与说明的新版本，但写入面只有一层：POST /briefs 与 POST /prototype-versions 产出 draft，canonical 指针不动；真正推进版本的是 POST /releases（人或按模块策略自动）。三道闸门依次卡在流水线上：基准不陈旧（base_version ≠ 当前版 → 409，强制 rebase）、不越权（实际改动 − 声明范围 − 白名单）、目标达成（acceptance[].check 逐条判定）。

画面 5 · 一条时间轴同时追踪原型与说明：版本号永不复用，回滚 = 发新版

三张表都是 append-only：module_brief_version、issue_prototype_version、module_release。任何一个旧版本都能在当前 UI 里打开看（只读）与 以它为基发起新提案，因此“谁在什么时点把哪条说明改成什么、对应原型哪一版”永远是同一个 release 行上的两个数字，审计不问自明。

为什么必须成对不信任一侧
只记原型版本 → 不知道当时说明写了什么；只记说明版本 → 不知道当时界面长什么样。二者错开就会出现“说明写着归档区只读、原型却没归档入口”的隐形不一致。module_release 的作用就是把两个数字锚在同一行，任何一侧单独前移都只能停留在 draft。
不可变性三条约束
① UNIQUE(module_id, version) 不重用版本号；② status 只允许 draft → published → superseded 单向前进；③ 删模块级联删版本（ON DELETE CASCADE），但删单版本没有接口——只能新发一版覆盖。
