# 日历 + 需求模块：现有动线与功能缺陷

- 日期：2026-09-06（代码实证）
- 结论：**画面按原型拼上了，动线仍是「建一张 Issue」。** 日历「＋新建需求」没有独立产品入口；创建后也不进入需求流水线。用户感觉「按图做了，但走不通」的根因在这里，不在色块样式。

对照：设计 `2026-09-04-requirement-calendar-design.md` 端到端流水线；提升设计要求创建后留在日历、色块点开抽屉。

---

## 0. 产品身份（先认清，再看动线）

| 概念 | 代码事实 | 用户以为 |
|---|---|---|
| 需求 | 任何 `parent_issue_id IS NULL` 的 issue | 日历里「排好期、配好班底」的一张需求 |
| 任务 | 有 parent 的子 issue，或用户在 Issues 里建的普通单 | 和需求是两类东西 |
| 创建需求 | **没有独立 API / 独立弹窗。** 日历按钮调用 `openCreateIssueWithPreference()` | 打开原型 f3 那张需求表单 |

服务端把「顶层 + 有项目」在创建时拷贝班底快照（`CopyProjectRoleDefaultsToIssue`）。没有项目的顶层 issue **同样是需求**（`root_requirement_id = 自身`），只是没有班底、没有日历字段。

因此：Issues 里随手建的 bug、Agent 快速创建的任务，都会变成「需求」，污染日历语义。

---

## 1. 设计动线（应该怎样走）

```
日历「＋新建需求」
  → 强制打开需求表单（项目 / 目标 / git 库 / 班底 / start_at / 拆解三模式 / 自动触发）
  → 提交后留在日历，色块出现，抽屉打开到当前阶段
  → 有原型师：生成原型 → 打点 → 确认门
  → 无原型师：跳过，进入拆解
  → decompose_mode=
       auto    → 创建后自动 POST /decompose，确认也可自动
       confirm → PM 出草稿后停在确认工作台
       manual  → 不派 PM，人直接填草稿再确认
  → 确认拆解后等 start_at（auto_trigger）或手动触发
  → 执行 → 验收
```

项目「需求详情」应能从本项目再建一张需求，走同一条线。

---

## 2. 现有动线（代码实际怎么走）

### 动线 A · 日历「＋新建需求」（主入口，错位最重）

```
日历页按钮
  → openCreateIssueWithPreference()   // 不传 project、不传「只要手动需求表单」
  → lastMode 默认 "agent"（create-mode-store）
       ├─ agent：Quick Create，零需求字段（无 goal / start_at / 班底 / 拆解模式）
       └─ manual：通用建任务弹窗
            └─ 需求字段仅当 !parent && projectId 才渲染（create-issue.tsx L346）
  → 提交 POST /issues（顶层 issue）
  → toast「已创建」+「查看任务」→ router.push(issueDetail)
  → 弹窗关闭；日历不主动开抽屉、不写 ?req=
```

**用户体感**

1. 点「新建需求」，出来的是 AI 建任务或一张任务单。
2. 没先选项目 → 原型 f3 整块字段不出现，填了也像普通任务。
3. 日历上的项目过滤**不会**带进弹窗。
4. 没填 `start_at` → `CalendarView` 不画色块 → 以为没创建成功。
5. 点 toast「查看任务」离开日历，和提升设计「不离开日历上下文」相反。

### 动线 B · 手动创建且选了项目（最接近原型，仍断）

```
手动弹窗选项目
  → 底部才露出需求字段（塞在长任务表单下面，max-h-64 小滚动区）
  → 提交写入 goal / start_at / decompose_mode / auto_trigger / repo
  → 服务端拷贝班底；前端若改过 RoleStrip 再 PUT 覆盖
  → 跳转 issue 详情（或停在原页但 toast 引导去详情）
  → 详情页底部 RequirementFlowSection
```

`decompose_mode` / `auto_trigger` **只落库**。`requirement-flow-section.tsx` **完全不读这两列**：

- `auto` 不会自动 `POST /decompose`，也不会跳过确认。
- `confirm` / `manual` 都要用户自己点「开始拆解」。
- 有原型师则停在「请先生成原型」，创建不会派 stage 1。

字段按原型画了，**创建后流水线不点火**。

### 动线 C · 日历色块 / 项目需求列表（查看与推进）

```
色块点击 → RequirementDrawer → FlowSection（同详情组件）
项目「需求详情」卡片 → 同一抽屉
项目「任务概览」里的 IssueSurface 日历 → CalendarView 无 onOpenRequirement
                                         → AppLink 跳 issue 详情
```

三条看需求的路，**两种交互**：工作区日历 / 需求 TAB 用抽屉；项目任务概览日历仍跳详情。

抽屉关闭不 invalidate 日历列表；确认拆解后色块状态经常不刷新。

### 动线 D · 项目「需求详情」TAB

只有列表，**没有「＋新建需求」**。要创建只能回日历或侧栏「新建」，再自己选对项目。本项目上下文断掉。

### 动线 E · Issues / 侧栏 / Cmd-K / 快捷键 `c`

全部 `openCreateIssueWithPreference()`。建出来的顶层 issue 带默认 `decompose_mode=confirm`、`auto_trigger=true`，在详情页也会挂上 FlowSection。普通任务和需求**入口不分、对象不分、事后面板却当需求渲染**。

## 3. 功能缺陷（按动线，不按画面）

### P0 · 创建入口用错产品

| # | 缺陷 | 证据 | 后果 |
|---|---|---|---|
| 1 | 日历「新建需求」走偏好弹窗，默认 Agent 快速创建 | `calendar-page.tsx` → `openCreateIssueWithPreference()`；`lastMode` 默认 `agent` | 主路径看不到 f3 任何字段 |
| 2 | 需求字段绑死「已选项目」 | `showRequirementFields = !parent && !!projectId` | 未选项目 = 普通建任务；日历过滤不预填 project |
| 3 | 创建后跳详情 / toast 引导去任务 | `router.push(p.issueDetail)` | 违反「留在日历 + 抽屉」 |
| 4 | 无排期则日历无色块 | `requirementSpan` 要 `start_at` 或 `due_date` | 创建成功但主画面空白 |
| 5 | 拆解三模式、自动触发创建后不生效 | FlowSection 不读 `decompose_mode` / `auto_trigger` | 用户选了「全自动」仍要手点开始拆解 |

### P1 · 对象与入口混用

| # | 缺陷 | 后果 |
|---|---|---|
| 6 | 顶层 issue ≡ 需求，Issues 创建污染需求轴 | 日历和 FlowSection 出现大量非需求单 |
| 7 | 项目需求 TAB 不能创建 | 档案侧只能看不能开单 |
| 8 | 工作区日历抽屉 vs 项目任务概览日历跳转 | 同一色块两种离开方式 |

### P1 · 流水线点不着

| # | 缺陷 | 后果 |
|---|---|---|
| 9 | 创建不派原型、不派 PM | 抽屉打开是「空阶段 + 一个按钮」 |
| 10 | f5 确认台过薄（见集成评估） | 即使走进拆解也审不了 |
| 11 | 确认 / 触发不刷新日历缓存 | 走完门，色块还停在旧态 |

### P2 · 壳与数据（放大动线断裂）

桌面无 `/calendar` 路由；列表每状态类目 50 条。见 [日历模块集成评估](./2026-09-06-日历模块集成评估.md)。这是「进得去、找得全」的问题，不是创建语义本身，但会让动线 A/C 更难被验证。

## 4. 现有流程 vs 设计流程（一张表）

| 步骤 | 设计 | 现状 |
|---|---|---|
| 入口文案 | 新建需求 | 文案对，调用的是新建任务 |
| 表单 | 需求专用（f3） | 任务表单 + 条件露出的附录字段 |
| 项目 | 必填 / 从日历带入 | 可选；日历过滤不带入 |
| 提交后 | 留在日历，开抽屉 | 关弹窗；toast 去详情 |
| 色块 | 立刻可见 | 无 `start_at` 则不可见 |
| 原型 | 有班底则自动或一键进入 | 详情/抽屉里再点生成 |
| 拆解模式 | auto/confirm/manual 分叉 | 只存字段，UI 一条「开始拆解」 |
| 触发 | 确认后按 `start_at` / 手动 | 机制在；创建经常到不了「已确认」 |
| 项目需求 TAB | 看 + 建 | 只能看 |

## 5. 收口策略（动线优先，不先画新控件）

原则仍是组装：不新建需求表，不新状态机。但**入口和创建后落地必须改语义**，不能再「按钮换皮、弹窗照旧」。

1. **日历 / 项目需求 TAB 的「新建需求」必须打开手动需求表单**，禁止走 `lastMode=agent`。可复用 `create-issue`，但调用时传入 `{ project_id, forceManual: true }`（或直接 `open("create-issue", …)`）。
2. **项目必填后才允许提交为需求**；日历当前过滤项目、项目 TAB 的 `projectId` 预填且锁定。
3. **`start_at` 对日历入口必填**（或默认「今天 09:00」），否则色块承诺无法兑现。
4. **创建成功：invalidate 日历列表 + 打开抽屉（`?req=`），禁止默认跳详情。** toast 可以留「在任务中打开」作次要动作。
5. **FlowSection 按 `decompose_mode` 点火**：`auto` 创建后（或过原型门后）自动 `decompose`；`confirm` 派 PM 后进确认台；`manual` 直接空草稿、不派 PM。现在的「开始拆解」只留给 confirm/manual 尚未发起的状态。
6. **Issues 通用创建保持建任务**；不要在无项目、无日历意图时把用户推进四阶段条。详情页 FlowSection 可改为「有项目且有需求字段 / 班底」才挂，避免普通顶层 issue 长出一条假流水线。

实施顺序建议：先做 1–4（创建动线闭环），再做 5–6（流水线点火与对象分离）。与 [日历模块集成改进方案](../plans/2026-09-06-日历模块集成改进方案.md) 的 C0 可并行：C0 解决「进得去」，本节解决「建得对、建完能接着走」。
