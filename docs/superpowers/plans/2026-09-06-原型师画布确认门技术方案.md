## 2. 已锁定的产品语义

### 2.1 「画布」是什么

**产品内原型画布** = 抽屉 / 详情里 f4 左栏的可交互预览面：

1. iframe 加载当前版本 HTML（沙箱，无父页 cookie）。
2. 右侧或底栏是**模块确认条**（不是画布里的装饰）。
3. 版本条可切 vN / 并排对照（P1）。

Cursor 画布若要用，只做 Agent 侧导航台（打开 `html_path`、发起「按 ✗ 模块重生成」对话），**确认结果仍只写 Multica**。

### 2.2 「功能模块」是什么

原型师生成时产出的 **屏幕 / 功能区块**，一条需求通常 3–8 块。每块必须带稳定 id。

```
module_id     稳定键，如 refund-apply / refund-timeline / refund-retry
title         展示名，如「退款申请页」
kind          new | modify   （与拆解 feature_points.kind 对齐，可空）
project_module_id?   可选归属日历模块，仅展示，不参与门禁
details[]     该块下的实现细节（沿用现有 PrototypeMark）
```

用户对模块的动作只有四种：

| 动作 | 效果 |
|---|---|
| ✓ 确认本模块 | 块内细节全部视为 ok；该块冻结，重生成默认保留 |
| ✗ 驳回 + 修正诉求 | 回流〔本轮修正〕；下一次生成必须改这一块 |
| ○ 待定 | **阻断整版确认**（相对画面 4 升级：原 ○ 只提示） |
| 显式忽略 | 本块不进原型、转 PM 拆解关注（对标画面 4 目标覆盖「后端约束 → 转拆解」） |

禁止：在 iframe 里直接改文案 / 拖控件写回 HTML。交互状态只用于**体验原型**，不写库。

### 2.3 确认门（相对画面 4 标注 9 的收紧）

整版「确认原型，进入拆解」当且仅当：

1. 当前版本 `status=pending`。
2. **每个模块**都是 `confirmed` 或 `ignored`（不得留 `pending`）。
3. 不存在未处理的 `verdict=no`（须重生成消解，或该模块改为 ignored）。
4. 至少存在 1 个 `confirmed` 模块（防止「全部忽略」空过门）。跳过整版仍走现有「⏭ 跳过原型」。

Server 与 UI 同一套判定，UI 禁用只是提示。

## 3. 总体架构

```
用户点「一键生成」
    → AssemblePrototypePrompt（五段 + 模块契约 +〔本轮修正〕）
    → 登记 issue_prototype_version (vN, pending)
    → 派发 stage 1 原型师子任务
    → Agent 写业务仓 docs/prototypes/<KEY>-<slug>.vN.html
    → 回写 marks[]（按模块分组的细节清单）

用户在原型画布
    → iframe 体验可交互状态
    → 按模块 ✓ / ✗ / ○ / 忽略
    → POST .../prototypes/{version}/marks   （仍是 whole-document）

✗ 模块 + 修正诉求
    → 重生成：旧 pending → superseded，version+1
    → 提示词〔本轮修正〕只带驳回模块
    → Agent 默认保留已 ✓ 模块的 DOM，只改 ✗ 模块

全部模块 confirmed | ignored
    → POST .../prototypes/{version}/confirm
    → 关 stage 1 barrier → PM 拆解
    → 已确认模块清单进入拆解对照（只读投影，不新表）
```

原则：**编排复用 454 + 现有三端点**；变的是 marks 形状、确认谓词、预览面、产出路径带版本号。

## 4. 数据：扩展 marks，不建新表

`issue_prototype_version` 列集不动。`marks` JSONB 从扁平细节升为「模块 + 细节」。

### 4.1 向后兼容形状

现网：

```json
[{ "detail_id": "①", "verdict": "ok", "note": "" }]
```

目标（新生成版本必须带 `module_id`）：

```json
[
  {
    "module_id": "refund-apply",
    "module_title": "退款申请页",
    "module_status": "confirmed",
    "kind": "modify",
    "project_module_id": null,
    "detail_id": "refund-apply.async-banner",
    "verdict": "ok",
    "note": ""
  },
  {
    "module_id": "refund-retry",
    "module_title": "失败重试",
    "module_status": "rejected",
    "kind": "new",
    "detail_id": "refund-retry.auto-escalate",
    "verdict": "no",
    "note": "去掉自动升级人工；重试上限 3"
  }
]
```

约定：

- 同一 `module_id` 的 `module_title` / `module_status` / `kind` 必须一致；server 以该组第一条为准做聚合校验。
- `module_status ∈ pending | confirmed | rejected | ignored`。
- 旧版本无 `module_id`：确认门回退为**现行规则**（只拦 `verdict=no`），避免存量 409。
- 新版本缺 `module_id`：生成回写视为失败，stage 1 子任务保持未终态，提示「模块清单未产出」。

不新增列。目标覆盖对照若要落库，进同一 JSON 的可选 `coverage[]`；没有就继续从 `issue.goal` 只读展示（日历 C3 已定）。

### 4.2 产出路径带版本号

现状 `PrototypeOutputPath` → `docs/prototypes/<KEY>-<slug>.html`，多版本互相覆盖，画布无法预览历史。

改为：

```
docs/prototypes/<KEY>-<slug>.v{n}.html
```

`html_path` 仍是版本行上的权威路径。不靠 git commit 做预览（回滚后置）。

### 4.3 TypeScript / Go 同步

`packages/core/types/api.ts` `PrototypeMark` 与 `service.PrototypeMark` 同步加可选字段：

```ts
export interface PrototypeMark {
  detail_id: string;
  verdict: "ok" | "no" | "pending";
  note: string;
  module_id?: string;
  module_title?: string;
  module_status?: "pending" | "confirmed" | "rejected" | "ignored";
  kind?: "new" | "modify" | "";
  project_module_id?: string | null;
}
```

Go 用 `json` omitempty，旧行能反序列化。

## 5. 确认门与提示词（server 只改谓词和〔产出〕段）

文件：

- `server/internal/service/prototype.go` — `ConfirmPrototypeVersion` / `validatePrototypeMarks`
- `server/internal/service/prototype_prompt.go` — 〔产出〕+〔本轮修正〕
- `server/internal/handler/requirement_prototype.go` — 错误文案映射
- 测试：`prototype.go` 同包测 + `requirement_prototype_test.go`

### 5.1 确认谓词

```
若 marks 全部缺 module_id
    → 现行：存在 verdict=no 则 409
否则
    → 按 module_id 分组
    → 任一组 module_status=pending 或组内存在未 ignored 的 verdict=no → 409
    → 零组 confirmed → 409（空确认）
    → 通过则 status=confirmed
```

`module_status=rejected` 且组内仍有 `verdict=no`：与现行一样，**必须重生成才能消解**，忽略才能过门。备注不能替代重生成。

### 5.2 提示词增量（仍是一段字符串，不新协议）

〔产出〕追加模块契约，Agent 必须同时满足：

1. 单文件 HTML，可本地打开，可交互（tab / 表单 / 状态切换用纯前端）。
2. 每个功能模块包在：

```html
<section data-proto-module="refund-apply" data-proto-title="退款申请页" data-proto-kind="modify">
  ...
</section>
```

3. 同文件末尾（或约定 `<script type="application/json" id="proto-manifest">`）给出模块 + 细节清单，供任务结束时写入 `marks`。
4. 已 `confirmed` 的 `module_id`：**不得改 DOM 结构与文案**；只改 `rejected` 模块。
5. 风格继续「沿用业务仓 token，不引入新组件库」。

〔本轮修正〕按**模块**聚合，不再只列细节 id：

```
〔本轮修正〕refund-retry：去掉自动升级人工；重试上限 3。保留模块：refund-apply, refund-timeline。
```

### 5.3 API 不动

| 方法 | 路径 | 变化 |
|---|---|---|
| GET | `/issues/{id}/prototypes` | 响应多几个可选字段 |
| POST | `/issues/{id}/prototype/generate` | body 仍 `{ marks?, prompt_append? }` |
| POST | `/issues/{id}/prototypes/{version}/marks` | 仍 whole-document；校验新枚举 |
| POST | `/issues/{id}/prototypes/{version}/confirm` | 谓词收紧，路径不变 |

禁止新增 `/modules/{id}/confirm`。模块确认 = 改该组 `module_status` 后 PUT marks。

## 6. 前端：只加深 f4 面板

唯一主改：`packages/views/issues/components/requirement-prototype-panel.tsx`  
宿主不动：`requirement-flow-section.tsx`（抽屉与详情共用）。

### 6.1 左栏 = 原型画布

| 块 | 行为 |
|---|---|
| 版本条 | 当前 vN；点击历史版切换 iframe `src`（`html_path` 经已有 artifact / 静态代理；Web 读不到本地仓时走「打开交付物」降级，与档案线一致） |
| iframe | `sandbox="allow-scripts"`，禁止 `allow-same-origin`；父页不读业务 cookie |
| 模块框 | 画布外的模块条，不靠穿透 iframe DOM。清单来自 marks 聚合，不解析 HTML |
| 全屏 | 现有「打开全屏预览」语义：新窗口打开同一 `html_path` |

**为什么不解析 iframe DOM：** Web 端本来就不保证能读业务仓；marks 是确认事实源，HTML 是体验面。两边靠 Agent 同时写，允许短暂不一致，以 marks 为准。

### 6.2 模块确认条（每个模块必须点一次）

每个模块一行：

- 标题 / kind 标签 / 细节计数（✓n · ✗n · ○n）
- 四按钮：确认 / 驳回 / 待定 / 忽略
- 驳回时必填修正诉求（沿用现 note 校验）
- 点「确认」→ 组内细节一律 `ok`，`module_status=confirmed`
- 点「驳回」→ `module_status=rejected`，至少一条 `verdict=no` + note

整版确认按钮：任一模块 `pending` 或存在未消解 `no` → disabled + 红字（列出模块名）。

### 6.3 右栏

保持画面 4：五段提示词（灰底只读）+〔本轮修正〕红底 + 一键生成 / 按提示词重生成 + 版本历史 + 目标覆盖只读。

重生成按钮文案区分：

- 无驳回：`↻ 按提示词重新生成（整版 +1）`
- 有驳回：`↻ 只重做 N 个驳回模块（版本 +1，已确认模块保留）`

语义都是现有 generate；差别只在 marks →〔本轮修正〕内容。

### 6.4 可交互状态的边界

| 允许 | 禁止 |
|---|---|
| 在 iframe 里点 tab、填表、看空态 / 错误态 / 成功态 | 把 iframe 内操作当成确认 |
| 多版本切换对照同一条用户路径 | 在画布里改 HTML / 改 token |
| 追加一条「原型未覆盖」细节（画面 4 已有） | 追加后不经模块确认就过门 |

用户对产品功能的调整路径只有：**驳回模块 → 修正诉求 → 重生成 → 再确认**。这是「避免随意修改」的唯一闸门。

## 7. 与下游的衔接（不改拆解 API）

确认后，PM 拆解（画面 5）只读投影：

- 已 `confirmed` 模块 → 默认带入 `DecomposeFeaturePoint` 草稿标题（`title=module_title`，`kind` 原样，`detail` 拼该组细节）。
- `ignored` 模块 → 进入目标覆盖「转拆解关注」，不自动建子任务。
- 实现：`requirement-decompose-panel` 从最新 `confirmed` 版本的 marks 聚合；确认拆解 body 仍是 `{ drafts }`。

`requirement_decompose.go` 已有「最新原型 `status==confirmed`」读取，不新开接口。

## 8. 波次与验收

对齐日历「先能用再加深」。本方案是 f4 的加深，不插入 C0/C1。

| 波次 | 目标 | 改哪些 | 不做 |
|---|---|---|---|
| **P0 模块门** | 新版本必须带 module_id；确认要逐模块点过；○ 阻断 | `PrototypeMark` 字段；`ConfirmPrototypeVersion` 谓词；面板模块条；prompt 〔产出〕/〔本轮修正〕 | iframe、路径改版号 |
| **P1 画布预览** | iframe 体验可交互 HTML；版本切换；路径 `.vN.html` | `PrototypeOutputPath`；面板左栏预览；版本条 | 并排 diff、打点穿透 |
| **P2 对照与保留** | 双版并排；重生成提示「保留已确认模块」 | 面板布局；prompt 保留清单；decompose 只读带入 | git 回滚、在线编辑、Cursor 画布宿主 |

### P0 验收

- [ ] 生成后模块条出现，整版确认在全部模块 ✓/忽略前不可点。
- [ ] 留一个 ○ → server confirm 409，文案带模块名。
- [ ] ✗ 且 note 为空 → 不能保存 marks（现有）。
- [ ] ✗ + note → 重生成后旧版 superseded，新版 pending，〔本轮修正〕含该模块。
- [ ] 无 `module_id` 的旧版本仍按现行门禁通过（兼容）。
- [ ] 全部忽略 → 409；跳过原型仍可用。
- [ ] 未启用原型师 → stage 1 仍跳过（回归）。

### P1 验收

- [ ] 当前版本 iframe 能点出至少一种状态变化（由 Agent 产出的 HTML 自带）。
- [ ] 切到 v1 / v2 预览互不覆盖（路径含版本号）。
- [ ] Web 读不到文件时预览降级为路径 +「打开交付物」，不假渲染。

### P2 验收

- [ ] 并排时已确认模块两侧 DOM 契约一致（人工对照即可，不做像素 diff）。
- [ ] 拆解面板能看到已确认模块列表，确认拆解 API 形状不变。

## 9. 风险与纪律

| 风险 | 处理 |
|---|---|
| Agent 漏写 `data-proto-module` / marks 无 module_id | P0 把「新版本缺 module_id」视为生成未完成，不放行确认 |
| 用户把 iframe 内点击当成已确认 | 确认只认模块条；画布上常驻「体验 ≠ 确认」 |
| 与日历 C3「f4 后置打点」冲突 | 本方案用**画布外模块条**，不做预览就地打点，不破 C3 |
| Cursor 画布被再次当成宿主 | 产物只允许 `docs/prototypes/*.html` + `issue_prototype_version` |
| 模块切太碎 / 太粗 | 提示词约束 3–8 块；用户可「追加细节」，不可在 UI 里拆合模块（拆合走驳回重生成） |

## 10. 建议开工顺序

1. 先做 **P0**：类型 + 确认谓词 + 模块条。一天内可在现面板验证「每个模块必须确认」。
2. 再做 **P1**：iframe + `.vN.html`，才谈得上「画布上快速看不同版本」。
3. **P2** 等 P0 门禁被真实需求跑过一轮再做，避免先做对照布局。

不需要先迁 HTML 深稿进 `.canvas.tsx`。画面 4 仍是交互语义源；本文件是落地契约。
