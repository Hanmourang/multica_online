② 端到端流水线 — 四 stage + barrier 门 + 打回环

stage 编号 1-based（复用 migration 123）。启用原型师才有 stage 1，停用则跳过；stage 之间由 barrier 门隔离——上一 stage 全部子任务终态才唤醒下一 stage 责任人。验收不通过打回 stage 3（上限 3 轮，超限转人工）。

验收
测试 · Vera（停用则回落 PM）
  • 依据：已确认原型 + plan + 验收代码 + 图谱
  • 执行 acceptance/*.spec.ts（版本绑定）
  • 四板块报告：溯源/执行/回归/目标覆盖

↩ 打回环：验收不通过 → 定位失败断言 + 图谱反查 → 新建 stage 3 修复子任务（依赖挂到相关任务）→ 修复终态后 barrier 再唤醒验收。轮次上限 3，超限需求转「验收失败」并通知负责人 + PM，终态即释放模块占用。
定时触发语义：jobs_requirement_trigger.go 每 30s 扫描 auto_trigger=true ∧ triggered_at IS NULL ∧ decomposition_confirmed_at IS NOT NULL ∧ start_at ≤ now() 的需求，同事务写 triggered_at 防重 → 无未完成依赖的 stage 3 子任务入队。改期（拖拽/PATCH）在触发前自由，触发后拒绝（409）。手动触发按钮走同一函数，忽略 start_at。

④ 需求状态机 — 8 态派生投影（不落列，SQL 计算）

与 issue_effective_status 同一思路：日历色块与详情状态由子任务 stage/status + 队列状态实时派生，永远与事实一致。主流程一条直线；「等待模块释放」是执行期的可逆分支；「验收不通过」打回执行（≤3 轮）。

state machine — derived projection
○ 未拆解 无 stage2 子任务 →发起拆解 ⚠ 拆解待确认 confirm 模式 →确认拆解
写 confirmed_at ⏱ 待触发 start_at 倒计时 →到点/手动触发
写 triggered_at ▶ 执行中 N/M 进度 →stage 3 全终态
barrier 唤醒 🧪 验收中 stage 4 →验收通过 ✅ 已完成
🎨 原型待确认 启用原型师时前置 →确认门通过
（无未处理 ✗） 进入「⚠ 拆解待确认 / ○ 未拆解」 🔒 等待模块释放 组间互斥 ⇄ 与「▶ 执行中」互转：他组持有同模块 → 等待；对方组终态即释放 → 按 start_at 升序唤醒 ↩ 验收不通过：建 stage 3 修复子任务 → 回到「▶ 执行中」；轮次上限 3，超限 → 需求转「验收失败」（终态，释放模块，通知负责人+PM）

⑤ 部署视图 — server 集中编排 · daemon 分布执行 · agent 端 MCP 直连 GitNexus

调度与状态全部收敛在 server 单点（Postgres 为事实源）；daemon 只负责任务执行与模块锁持有；GitNexus 由 agent 端经 MCP 自主查询（已确认决策，server 不落图谱快照，仅把查询结果以 graph_context JSONB 存到子任务上）。
