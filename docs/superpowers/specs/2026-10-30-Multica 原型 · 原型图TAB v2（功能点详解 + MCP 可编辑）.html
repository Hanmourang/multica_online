  • 为什么必带 base_version：说明是人机共写的，没有乐观锁就会出现「AI 拿旧底稿覆盖人工刚写的一段」。带版本号 + 409 才能把冲突交回给调用方而不是默默丢失。
  • 为什么每次写都成版本：因为右栏的「来源 + 版本」标签、版本记录回放、agent 越权审计全靠它；如果只存最新值，三类追溯全部失效。

画面 6 · 版本记录：每次编辑一行，说明与原型各一本账

两条时间轴：说明轴（brief v1…v4，人与 AI 共写）与原型轴（proto v1…v4，文件驱动）。两轴各自 append-only，发布时用 module_release 把「哪版说明 + 哪版原型」绑成一个成对版本（R1…R3）。右栏版本记录是说明轴的投影；原型轴在顶部下拉里看。

版本记录 · 说明轴与原型轴成对发布append-only

R3成对人工发布brief v3 + proto v3—当前权威回滚（以旧为基发新版）
三条不可变性
序号不复用删掉的版本号不会回收；新写入永远 max+1
旧版不可改只有 status 可从 draft → published → superseded
指针单写点只有 release.publish 能改 canonical_prototype_version / brief_version
所以「AI 自主迭代」不会把历史抹掉：它只会不断加行，人随时能在时间轴上逐行回看是哪个 run、哪些字段、加减多少。
回滚不等于删除
点「回滚到 R1」→ 读取 R1 的 brief v1 + proto v1 → 以它们为 base 生成 brief v5 / proto v5 → 再成对发布为 R4。好处：①历史完整；②报告与审计不会出现“版本消失”；③回滚动作本身也是一次可追溯的变更（source=rollback）。
对应接口：POST /modules/{id}/releases/{v}/rollback，请求体只传目标 release 号，不传内容。

画面 7 · 契约：字段字典一份、后台工具七个、前端落点三处

要把「哪些字段可写、哪些只能由库算」写死在代码里，最省事的做法是把字段字典存表（module_field_def）：右栏照着它渲染、服务端工具的 inputSchema 也照着它生成。一份定义两处用，不会出现“界面能改但后台改不了”或反之。这些工具名不进产品界面——界面只呈现「人工 / AI 自动更新」与版本号，本节供研发对齐契约。
