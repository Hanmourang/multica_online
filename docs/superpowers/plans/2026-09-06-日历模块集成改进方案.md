# 日历模块集成改进方案

- 日期：2026-09-06
- 上游 Gap：`../specs/2026-09-06-日历模块集成评估.md`
- 产品契约：`../specs/2026-09-06-calendar-module-elevation-design.md`
- 原型：`../specs/2026-09-04-rMultica 原型 · 需求日历 + 角色化流水线.html`
- 原则：**组装优先，零新机制。** 不新建需求表、不给日历单独状态机、不改确认 / 触发 API 语义、Web 不连 GitNexus。

与 `2026-09-06-capability-gap-remediation.md` 的关系：那份覆盖日历 + 档案 + W4 运行时。**本文只收口日历线**——把评估里已落地的 W1 骨架之后的缺口，拆到具体模块、改法和验收。档案 W3 / 改 parent 重算 root 仍走原方案，不在此重复。

## 0. 策略

按「用户能不能用 → 能不能找全 → 能不能审」三层推进，禁止先做 f5 深工作台却让桌面日历 404。

| 波次 | 目标 | 人日 | 不做什么 |
|---|---|---|---|
| **C0 止血** | 桌面能进页；日历看到工作区全部顶层需求；抽屉操作后色块刷新 | 1–2 | 不改看板 `issueListOptions` 的 50 条分页语义 |
| **C1 提升闭环** | 工具栏三件、抽屉头班底、列表卡进度、`?req=` 回放 | 2–3 | 不做精确 PM 列表投影（避免 N+1 / 新列） |
| **C2 日历交互** | 色块角色头像 / 触发日 / held-by / grip 改窗长 / 改期互斥预检 | 3–4 | 不做资源负载均衡、不做新互斥服务 |
| **C3 工作台** | f5 加深（主）；f6 预检清单；f7 四板块只读加深 | 6–9 | 不改确认 API；f4 就地打点 / 回滚 commit **后置** |

**总策略四条**

1. **独立查询键，不蹭看板缓存。** 看板 `fetchFirstPages` 按 7 个 status_category 各取 50 条，是看板设计。日历另开 `calendarIssuesOptions`，用已有 `top_level_only=true` + 甘特同款 500 条翻页。
2. **过滤全在客户端。** `requirement_status` 是 SQL CASE 派生列，禁止把它做成 server filter。
3. **面板只改一处。** f4–f7 加深只动 `packages/views/issues/components/requirement-*-panel.tsx`。抽屉和详情页都挂 `RequirementFlowSection`，改一次两处生效。
4. **先读后写。** 互斥预检、held-by、班底全部复用已有投影 / `issueRolesOptions` / `triggerPreflight` 原因串。缺展示就补 UI，不补机制。

## 2. Gap → 模块 → 改法

### 2.1 壳与数据（评估 §1 P0 + §3.1–3.2）

#### Gap A · Desktop 日历 404

| 项 | 内容 |
|---|---|
| 现象 | 侧栏有「日历」，`appRoutes` 无 `calendar`，点进去无匹配路由 |
| 模块 | `apps/desktop/src/renderer/src/routes.tsx` |
| 改法 | 在 `issues` 与 `projects` 之间加 `{ path: "calendar", element: <CalendarPage />, handle: { title: "Calendar" } }` |
| 复用 | `CalendarPage` 已从 `@multica/views/calendar` 导出；`sanitizeTabPath` 接受任意 `/{slug}/…`，**不必改 tab-store** |
| 验收 | 桌面侧栏 / Cmd-K「日历」都能进页，与 web 同一套月周视图 |
| 测试 | desktop 路由表单测：`appRoutes` 含 `calendar`；或 renderer 导航 smoke |

#### Gap B · 日历不是全量需求

| 项 | 内容 |
|---|---|
| 现象 | `calendar-page` / `requirement-list-panel` 共用 `issueListOptions` → `fetchFirstPages`，每 status_category 只取首页 50 条。工作区需求一多，色块和列表会丢 |
| 模块 | `packages/core/issues/queries.ts`（主）；两处视图改 query hook |
| 改法 | 新增独立缓存，**禁止**改看板 `ISSUE_PAGE_SIZE` |
| 不做 | 不为日历加新表 / 新 list 端点。`GET /api/issues?top_level_only=true` 已存在（`issue.go` L1531） |

```
issueKeys.calendar(wsId) = [...issueKeys.all(wsId), "calendar"]

calendarIssuesOptions(wsId):
  GET /api/issues
    top_level_only=true
    limit=500, offset 循环直到 total
    封顶与甘特相同 PROJECT_GANTT_MAX_ISSUES=10_000
  不传 scheduled=true
    —— scheduled 只认 start_date/due_date，会丢掉「无排期但有派生状态」
       的待确认需求（列表卡和待确认 chip 需要它们）
```

客户端再滤：日历色块仍要求 `start_at || due_date`；列表卡保留 `start_at || due_date || requirement_status`。

列表面板改为 `calendarIssuesOptions` + `project_id` 客户端滤，或同 query 加 `project_id` 参数（同一 key 家族：`issueKeys.calendar(wsId, projectId?)`）。优先**一个工作区 query**，项目 tab 客户端滤，避免两套翻页。

#### Gap C · 抽屉关了色块不刷新

| 项 | 内容 |
|---|---|
| 现象 | `RequirementFlowSection` 确认 / 触发 / verdict 只失效 `children` / `decomposition` / `detail` / `prototypeVersions`。日历吃的是 list 缓存，色块 `requirement_status` / `stage_progress` 不更新 |
| 模块 | `requirement-flow-section.tsx`（主）；`requirement-drawer.tsx`（关抽屉补一刀） |
| 改法 | 四处 mutation 成功后追加 `invalidateQueries({ queryKey: issueKeys.calendar(wsId) })`。关抽屉再 invalidate 一次作兜底（评估 §3 原文） |
| 策略 | 失效写在 FlowSection，详情页同一操作也会刷新日历——这是对的，两处共享 `issueKeys` |
| 验收 | 抽屉里确认拆解 → 关抽屉 → 色块从「拆解待确认」变成下一态，进度比更新 |

### 2.2 提升设计未做满（评估 §1 工具栏 / 抽屉头 / 列表卡）

#### Gap D · 工具栏少 PM / 拆解状态 / 待确认 N

| 控件 | 数据依据 | 实现 |
|---|---|---|
| 项目 | `issue.project_id` + `projectListOptions` | **已有** `<select>` |
| PM | 列表无角色投影。v1 用顶层 `assignee_*` 近似；下拉选项 = 当前日历结果集里出现过的责任人 | **C1**。精确 PM = `GET /issues/{id}/roles` 会 N+1，不做。痛了再加 list 投影 `pm_assignee`（另开后端波次） |
| 拆解状态 | `requirement_status` 字面量（10 态中的日历相关子集） | 客户端 `<select>`，选项由结果集去重，另加「全部」 |
| 待确认 N | `requirement_status ∈ {原型待确认, 拆解待确认}` | 右侧 chip，`N` = 过滤前计数；点击 = 把状态过滤设成这两态（toggle） |

模块：只改 `calendar-page.tsx` + `locales/*/calendar.json` 四语言。`CalendarView` **不**接收过滤逻辑。

测试：`calendar-page.test.tsx` 补三件（提升设计 §6 原文就要求，现状测试只覆盖项目过滤）。

#### Gap E · 抽屉头无班底头像

| 项 | 内容 |
|---|---|
| 模块 | `requirement-drawer.tsx` |
| 复用 | `issueRolesOptions(issueId)` + `ActorAvatar`（FlowSection / 测试里已 mock） |
| 改法 | 头栏在 10 态徽标旁渲染启用中的角色头像（prototyper / PM / developer / data / tester），disabled 灰显或隐藏（与 RoleStrip 一致即可） |
| 验收 | 打开抽屉即可看到班底，不必滚到面板内部 |

#### Gap F · 列表卡无班底、无阶段进度

| 项 | 内容 |
|---|---|
| 模块 | `requirement-list-panel.tsx` |
| 进度 | `issue.stage_progress` 已是列表投影列，**直接渲染**，零请求 |
| 班底 | 卡片多，禁止每卡 `listIssueRoleAssignments`。C1：**先只渲染进度**；班底放 C1 末或 C2，用 `useQueries` 对当前项目需求批量拉 roles（同项目通常 << 50） |
| 策略 | 进度是「免费」的，先做。班底是体验，可落后半步 |

#### Gap G · 无 `?req=` 回放

| 项 | 内容 |
|---|---|
| 模块 | `calendar-page.tsx`；项目需求 tab 用 `?view=requirements&req=` |
| 改法 | `useSearchParams`：开抽屉 `replace` 写入 `req`；关抽屉删掉。刷新 / 分享链接可回放 |
| 对齐 | 档案 `?view=` 同一模式；**不要** push，避免弄脏历史栈 |
| 注意 | 日历页**不要**挂 `useIssueViewUrlSync`（那是 Issues 视图枚举） |

### 2.3 原型 f1 / f2 日历交互（评估 §2）

全部落在 `calendar-view.tsx` 的 `RequirementBlock` + `handleDrop`，页面层只提供数据。

| Gap | 现状 | 改法 | 数据从哪来 |
|---|---|---|---|
| 色块当前阶段角色头像 | 只有状态图标 + 标题 + `stage_progress` | `segment==="start"` 时在标题前加一颗 `ActorAvatar` | 派生：未拆解/待确认 → PM；原型待确认 → prototyper；执行/等待 → developer；验收 → tester。C2 若已有 roles 映射表则用真 assignee，否则用 issue.assignee |
| 已拆解标自动触发日 | 色块只写状态字 | 已确认且未触发：在色块尾标 `start_at` 的日+分（如 `9/12 09:00`） | `issue.start_at` + `decomposition_confirmed_at` + `triggered_at`（后两者在 GetIssue；列表若无 confirmed 列，用 `requirement_status` 已拆解/待触发 近似） |
| 组间互斥「谁在等谁」 | 仅「等待模块释放」图标 | tooltip / 色块副文案：`held by 需求 #{n} {title}` | **先组装、不新 API。** 同一次 `calendarIssues` 结果里，按 `module_id` 找其他顶层需求中 `requirement_status` 为执行中 / 等待模块释放的占用方。对不上就只显示状态字，不编造标题 |
| 源格残影 + 浮动新旧日期 | 只有目标格 ring | drag 期间源块 `opacity-40`；跟随指针的小条显示 `旧 start → 新 start` | 纯 UI，`handleDrop` 已有 day delta |
| 右缘 grip 拉伸 `due_date` | 整块拖只平移窗，窗长不变 | `segment==="end"` 右侧 6px grip；`resize` 只改 `due_date`，`start_at` 不动；已触发仍 409 | `useUpdateIssue`，与现拖拽同一 mutation |
| 改期后互斥预检 | 只 PATCH | 落点后、或 grip 松手后：用**本页已加载的需求**算同模块是否将被占用；冲突则 toast「改期后可能与 #{n} 互斥」+ 仍提交（预检不阻断，与触发 409 分工：触发是硬门，改期是提示） | 零后端。真硬门仍是 `POST /trigger` 的 `module_window_busy` |

**C2 不做：** 为预检新增 `GET /trigger/dry-run`。`triggerPreflight` 已在 server 纯函数里，C3 若 PM 强烈要五件清单，再把同一函数暴露成只读 GET——那是「暴露已有判定」，不是新机制。

创建弹窗字段已齐。日历「＋新建需求」继续 `openCreateIssueWithPreference()`。

#### f5 拆解确认 — 日历线最大产品缺口

| 图谱四要素 | 从 `graph_context` 抽 nodes / code_objects / dependencies / impacts |
| 重新查询 | 写 `@PM 请重跑 /impact-analysis` 评论，走既有 trigger。**不**连 GitNexus |
| 验收规约 | path / version / assertions / cases，不再只抽 name |
| 折叠 + 执行人高亮 | 首卡展开；`initialAssignee` 快照 → `.asg.edit` |
| KV `decompose_mode` | 文案映射 auto / confirm / manual |

确认 API 三类校验（kind / 班底 / 同模块依赖）**不动**。

#### f6 调度 — 把 409 原因变成清单

| 已有 | 缺口 | 改法 |
|---|---|---|
| 倒计时、手动触发、互斥 banner、stage3 列表 | 五件预检只在 toast | C3：面板顶部固定 4 行（与 `triggerPreflight` 对齐）：拆解已生效 / 依赖无环 / 验收代码存在 / 互斥窗口。前三项用**已加载的** `decomposition_confirmed_at`、children `blocked_by`、stage3 `acceptance_spec` 客户端推；互斥窗口用同模块占用（与色块 held-by 同一函数）。点触发仍走 POST，409 映射到对应行标红 |
| DAG 可视化 | 无 | C3 用 children + `blocked_by` 做简单列表依赖，不上独立图引擎 |

原型写「五件」含「执行人在线」。服务端 v1 **故意不做**该预检（daemon 心跳 / claim 已覆盖）。UI 清单按 **4 件**画，不要第五件假绿灯。

#### f7 验收 — 只读加深，不新仲裁

| 已有 | 缺口 | 改法 |
|---|---|---|
| 轮次、pass/fail、修复链 | 依据溯源 / 代码执行 / 图谱回归 / 目标覆盖 | 从 stage4 子任务 / `acceptance_spec` JSON 抽得到的字段做四块只读；抽不到的块显示「档案未就绪」，**不造假数据** |
| 断言行号、版本约束 | 无独立 UI | 有 `assertions[]` / `version` 就渲染；没有不加编辑器 |

## 5. 风险与顺序依赖

1. **C0 必须先于 C1。** 过滤做在残缺的 50×7 列表上，待确认 N 会算错。
2. **`issueKeys.calendar` 必须挂在 `issueKeys.all(wsId)` 下。** 现有 `invalidateQueries(issueKeys.all)` 的 WS 更新器会顺带刷新日历；不要做成无 ws 前缀的孤儿 key。
3. **C2 held-by 是启发式。** 同模块多组并行时取「非自己且处于占用态」的第一条。不准时降级为状态字，禁止为了标题去扫 daemon。
4. **C3 与日历页无文件重叠**（除 FlowSection invalidate 已在 C0 做完）。C3 可与 C2 并行，但不要和 C0 抢 `queries.ts`。
5. **项目任务概览 IssueSurface 日历**继续跳详情或日后也接 `onOpenRequirement`——C2 给 `CalendarView` 的 `onOpen` 已存在，项目面要抽屉属于另一次产品决策，本方案不改 `project-detail.tsx` modes。
