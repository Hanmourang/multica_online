## 1. 系统现状：已具备什么

### 1.1 产品底座

Multica 是「多 agent 工作区 + issue 轴」：需求 = 顶层 issue（`parent_issue_id IS NULL`），子任务带 `stage`，组标识是 `root_requirement_id`。四阶段流水线只做编排，复用 stage barrier、依赖 DAG、ModuleLocker、autopilot 调度范式——**不发明新运行时**。

档案线以 **Git 为文档唯一事实源**，DB 只存 `rel_path + blob_sha` 与元数据；图谱/本体以 JSONB 快照入库；申报就绪度按 must / conditional / aux 三档契约聚合。

两条线共享同一条 issue 轴：日历管「何时跑、谁跑、跑到哪」，档案管「产出落在哪、能不能申报」。

### 1.4 刻意不做（已定稿，评估时不得当缺陷）

- 不做资源负载均衡、需求模板市场、验收代码在线编辑器、跨项目依赖。
- GitNexus **agent 端 MCP 查询**，server 不读文件系统、不做实时图谱查询。
- 本体层等抽取器就绪后自动点亮，UI 保持降级。
- Web 不能读本地档案目录，因此浏览器「同步」只能重校验，不能提交空清单（会误软删）。
- 「从模板创建」属 CLI（要落盘 + commit），Web 侧禁用是正确边界。

### 2.2 已被提升设计推翻、但代码未动的 IA

`2026-09-06-calendar-module-elevation-design.md` 已确认：

1. 日历与任务/项目**平级**，侧栏一级入口 `/calendar`
2. Issues 下的日历 tab **彻底移除**
3. 色块点击用**页内抽屉**承载四阶段，不跳详情
4. 项目详情「概览」改名「任务概览」，右侧加「需求详情」TAB

**实证：导航已预埋，页面壳为 0。** `paths.calendar`、侧栏 `NavKey`、`CalendarDays`、四语言 `nav.calendar` 已在；`packages/views/calendar/` 与 `apps/web/.../calendar/page.tsx`、desktop `routes.tsx` 的 calendar 路由均不存在——侧栏点击会 404。`issues-page.tsx` 仍把 `calendar` 放进 `modes`；`issues-header.tsx` 的日历 RadioItem **写死、未按 modes 门控**；色块 `href={paths.issueDetail(...)}`；`project-archive-views.tsx` 无 `requirements` tab。

这是用户「找不到需求模块」的产品根因——导航声明了日历，但没有落地页；同时任务子视图还占着日历。

### 2.3 f5 深挖（原型锚点 `#f5`）

原型约定：本画面**只做拆解**。左栏 = 只读基础信息 + 结构化 plan + 依赖总览；右栏 = 可编辑子任务明细；确认后批量生成自动化任务。

| 原型约定 | 现状（`requirement-decompose-panel.tsx`） | 影响 |
|---|---|---|
| plan 分目标分解 / 阶段划分 / 风险；与拆解不一致高亮 | `plan` 整段 `whitespace-pre-wrap`，无结构、无对照 | PM 无法在确认门审 plan 质量 |
| 功能点可增删，必须标新增/改造，待定禁止确认 | 仅 kind 切换；不可增删、无实现细节编辑 | 门只挡住「没打标」 |
| 图谱四要素 + 「重新查询」 | 能解析 `nodes` 则出芯片，否则不出框 | 影响面不可审、不可刷新 |
| 验收规约 path / version / assertions | 只抽 `cases[].name` | 确认时看不到将跑哪些断言 |
| 首卡展开其余折叠；改过的执行人高亮 | 全展开，无折叠、无 `.asg.edit` | 多子任务无法扫读 |
| KV 含拆解模式；修改回创建表单 | KV 无 `decompose_mode` | 丢失关键决策上下文 |
| 确认 → 批量建 stage 3/4 + 依赖 + 指派 | **后端已做** | 机制够，工作台不够 |

后端确认校验（fp kind / 班底内 / 角色启用 / 同模块依赖）已齐，**不要重做确认 API**。

## 4. 方案评估

### 4.1 三种路线

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. 组装优先** | 零新机制。日历提升复用 `CalendarView` + `RequirementFlowSection`；f5 加深现有草稿模型；档案把 461 端点接到控制台 | **采用** |
| B. 先补分析层 | 先做邻域 / 总线下钻 / 本体策略 | 局部可用，不作为本轮主线（GitNexus strategies 仍为空） |
| C. 再造需求对象 | 需求独立聚合根，或日历单独状态机 | **否决**（与 10 态派生、barrier、root 组锁全面冲突） |

### 4.2 为什么是组装而不是新建

1. 后端主链（拆解 → 触发 → 互斥 → 验收）已可跑通；再造状态机会制造第二事实源。
2. 提升设计已写明「零后端改动」——入口问题用路由 + 抽屉就能解。
3. 档案最大空转是「有 API 无消费者」（`bind-candidates`、真诊断），不是缺 DDL。
4. 团队已形成「诚实空态」纪律，继续填假数会破坏信任。

### 4.3 跨线风险

| 风险 | 级别 | 缓解 |
|---|---|---|
| 日历提升与档案抢 `project-archive-views` / locales | P0 | 日历只加 +1 tab 最小 diff，不重构档案组件（提升设计 §4b 已声明） |
| 改 `parent` 不级联重算 `root_requirement_id` | P0 | UpdateIssue 递归更新自身 + 子孙；否则组锁指错组 |
| WS3 未提交（locker 工作区改动） | P1 | 与档案无文件重叠，可单独提交；补 claim 闸门集成测试 |
| T21 前端全量 + Playwright 未做 | P1 | 先做一条创建→原型→拆解→触发→验收 e2e |
| 本体空转被误判为没做 | P2 | 保持降级文案，不进本轮承诺 |

## 5. 改进路线（四波）

每波有可演示出口。W1 / W2 可并行（文件冲突面小），W3 等档案前端稳定，W4 收运行时。文件级改动、接口契约、模块影响见 [补齐技术方案](../plans/2026-09-06-capability-gap-remediation.md)。

### W1 · 日历成为一级模块（6–8 人日，零后端）

- `paths.calendar` + `apps/web/.../calendar/page.tsx` + 侧栏 `CalendarDays`
- `calendar-view` git mv 到 `packages/views/calendar/`，Issues 去掉 calendar mode
- `requirement-drawer` 复用 `RequirementFlowSection`，与详情页共享 `issueKeys`
- 项目详情：概览改名任务概览；加「需求详情」列表，点卡片开同一抽屉

**出口：** 不离开日历上下文走完四阶段；项目里能列出并打开本项目需求。

### W2 · 把 f5 做成确认工作台（6–10 人日，前端为主）

- plan 三段展示 + 与子任务标题对照高亮
- 功能点增删改、待定红框、执行人改动高亮、卡片默认折叠
- 图谱四要素只读审阅；「请 PM agent 重查」走评论触发，**Web 不直连 GitNexus**
- 验收规约展示 path / version / assertions
- KV 补拆解模式

**出口：** 存在待定功能点无法确认；审完一张卡就能判断「拆得对不对」。不改确认 API 语义。

### W3 · 档案最后一公里（5–7 人日）

- 控制台读 `sync_diagnostics`，去掉推断阶段条
- 待绑定队列接 `bind-candidates`：conf ≥ 0.85 批量，低于人工
- 矩阵 JOIN issue 标题；`sync_config` 模式 / 冲突策略可写
- `migrate --apply` **单独向用户确认**后再跑

**出口：** 一次 sync 后能在控制台看到真失败项，并把 unbound 行绑到需求。

### W4 · 运行时收口（4–6 人日）

- 改 parent 级联重算 root；WS3 claim 组间互斥补测并提交
- 进度树展示 orphan 派生；override / 改派明确延期
- 一条日历全链路 Playwright
- filing PDF、图谱邻域、总线表级下钻：**不进本轮**

## 6. 建议决策

1. 本轮只做方案 A。成功标准按用户动作，不按表数量。
2. 非目标维持原 spec：不新建需求表、不给日历单独状态机、Web 不读文件系统、不把本体空表填假数据。
3. 并行纪律：日历提升对 `project-archive-views.tsx` 只做最小 diff；WS3 与档案无文件重叠，可先提交 locker。

**可演示的三条成功标准：**

- 从侧栏打开日历，点色块在抽屉里确认拆解，不跳详情页。
- 档案控制台把 unbound 行按置信度批量绑到需求。
- 一条已确认需求在 `start_at` 到点后自动入队，验收 fail 能打回 stage 3。
